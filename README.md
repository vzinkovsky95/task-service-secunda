# Task Service

[![CI](https://github.com/vzinkovsky95/task-service-secunda/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/vzinkovsky95/task-service-secunda/actions/workflows/ci.yml)

REST API для управления задачами в командах: роли (владелец, администратор, участник), история изменений
каждой задачи, комментарии, кеш списка задач в Redis и SQL-отчёт по команде.

Стек: Go 1.26 (стандартный `net/http`, `database/sql`, без ORM), MySQL 8.4, Redis 7, Docker Compose.

## Запуск

Нужны Docker и Docker Compose v2. Больше ничего ставить не нужно: Go и все его инструменты запускаются
в контейнерах.

```bash
scripts/init-env.sh
docker compose up --build -d
```

Первая команда создаёт `.env` из `.env.example` и подставляет случайные пароли MySQL и секрет JWT. Скрипт работает
на Linux и macOS, существующий `.env` не перезаписывает (чтобы создать заново, запустите с `--force`).
Секретов по умолчанию нет: без `JWT_SECRET` и данных MySQL сервис не стартует.

Через минуту все три контейнера должны быть `healthy`:

```bash
docker compose ps
curl http://127.0.0.1:18080/healthz
```

Сервис слушает `127.0.0.1:18080`, документация лежит на <http://127.0.0.1:18080/docs> (корневой адрес `/` ведёт туда же). MySQL и Redis опубликованы
только на `127.0.0.1` (порты `13306` и `16379`).

Остановить, не удаляя данные: `docker compose stop`. Запустить снова: `docker compose up -d`.
Логи приложения: `docker compose logs -f app`.

## Конфигурация

Всё настраивается переменными окружения. Для `docker compose` они лежат в `.env` (образец: `.env.example`).
В репозитории только образец, сам `.env` в git не попадает.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `APP_PORT` | `18080` | Порт приложения на хосте (`127.0.0.1`) |
| `MYSQL_PORT` | `13306` | Порт MySQL на хосте (`127.0.0.1`); внутри сети compose MySQL всегда на `3306` |
| `REDIS_PORT` | `16379` | Порт Redis на хосте (`127.0.0.1`) |
| `MYSQL_DATABASE` | `tasksvc` | Имя базы |
| `MYSQL_USER` | `tasksvc` | Пользователь базы |
| `MYSQL_PASSWORD` | нет, обязательно | Пароль пользователя |
| `MYSQL_ROOT_PASSWORD` | нет, обязательно | Пароль root (нужен контейнеру MySQL и интеграционным тестам) |
| `JWT_SECRET` | нет, обязательно | Секрет подписи JWT |
| `JWT_TTL` | `24h` | Срок жизни токена (`30m`, `24h`, ...) |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error`. На `debug` в лог попадают попадания и промахи кеша |
| `RATE_LIMIT_AUTH_PER_MINUTE` | `10` | Запросов в минуту на `register` и на `login` (отдельно каждый) с одного IP |
| `RATE_LIMIT_API_PER_MINUTE` | `120` | Запросов в минуту на пользователя для остальных маршрутов `/api/v1` |
| `TRUSTED_PROXIES` | пусто | IP или CIDR через запятую: прокси, которым можно верить в `X-Forwarded-For` |

Эти переменные `compose.yaml` задаёт приложению сам, в `.env` их указывать не нужно:

| Переменная | Значение в compose | Назначение |
|---|---|---|
| `HTTP_ADDR` | `:8080` | Адрес, который слушает приложение внутри контейнера |
| `MYSQL_HOST` | `mysql` | Хост MySQL |
| `REDIS_ADDR` | `redis:6379` | Адрес Redis |

Все контейнеры ограничены по памяти и процессору (`mem_limit` и `cpus` в `compose.yaml`), у MySQL и Redis
есть healthcheck, приложение стартует после них.

## Документация API

- Swagger UI: <http://127.0.0.1:18080/docs>
- Спецификация: <http://127.0.0.1:18080/openapi.yaml> (файл `api/openapi.yaml`, написан вручную)
- Документация на GitHub Pages: <https://vzinkovsky95.github.io/task-service-secunda/>. Это справочник: запросы с этой страницы
  не выполняются, пробовать API нужно на своём запуске.

Чтобы пробовать защищённые маршруты прямо в Swagger UI: выполните `POST /api/v1/login`, скопируйте поле `token`
из ответа, нажмите **Authorize** и вставьте токен (слово `Bearer` не нужно). Запросы уходят на тот же адрес,
с которого открыта страница.

Swagger UI загружается с CDN фиксированной версии `5.17.14` с проверкой хеша (SRI), поэтому странице нужен
доступ в интернет. Сам API и спецификация от интернета не зависят.

Спецификация не должна разойтись с кодом, это проверяют тесты (см. [Тесты](#тесты)): маршруты в `router.go`
и в `openapi.yaml` совпадают в обе стороны, коды ошибок тоже, а каждый ответ реального сервиса проверяется по схеме.

## Демо-данные и demo.sh

Обычный запуск данных не создаёт. Чтобы получить готовый стенд с пользователями всех ролей, запустите с профилем `demo`:

```bash
docker compose --profile demo up --build -d
```

Одноразовая служба `seed` ждёт, пока приложение станет `healthy` (то есть миграции применены), и заливает данные прямо в
базу, минуя API. Повторный запуск ничего не меняет: наличие демо-пользователя считается признаком загруженных данных.
Все даты считаются от момента загрузки. Данные только для демонстрации, в обычной конфигурации их нет.

У всех демо-пользователей один пароль: `demo-password`.

| Email | Имя | Роль |
|---|---|---|
| `demo-owner@example.com` | Анна Иванова | владелец команды «Разработка» |
| `demo-admin@example.com` | Борис Петров | администратор «Разработки» |
| `demo-member@example.com` | Вера Смирнова | участник «Разработки» и администратор «Маркетинга» |
| `demo-member2@example.com` | Глеб Кузнецов | участник «Разработки» |
| `demo-owner-b@example.com` | Дарья Орлова | владелец команды «Маркетинг» |
| `demo-outsider@example.com` | Егор Волков | не состоит ни в одной команде |

В данных две команды, 15 задач во всех трёх статусах, история изменений и комментарии. Шесть задач «Разработки» закрыты
за последние 30 дней, одна закрыта 35 дней назад и в отчёт не попадает, поэтому в топе исполнителей Вера 3, Глеб 2, Борис 1.

`scripts/demo.sh` проходит весь путь через `curl`: роли и изоляция команд на демо-данных, отчёт, затем на новых
пользователях права на поля, конфликт версий при двух одновременных `PUT`, курсорная пагинация, удаление участника
и ограничение частоты. Каждый ответ сверяется с ожидаемым кодом, при расхождении скрипт завершается с ненулевым кодом.

```bash
scripts/demo.sh
```

Нужны `bash`, `curl` и `sed`. Первая часть (демо-данные) пропускается, если профиль `demo` не запускали. Скрипт можно
запускать повторно: он сам создаёт новых пользователей и команду. Он укладывается в лимит 10 регистраций и 10 входов
в минуту с одного IP; если вход упёрся в лимит, скрипт ждёт `Retry-After`. Адрес можно сменить переменной `API`.

## Примеры запросов

Сквозной сценарий: две учётные записи, команда, задача, конфликт версий, история, отчёт. Команды выполняются
подряд в одной оболочке. Для разбора ответов хватает `sed`.

```bash
API=http://127.0.0.1:${APP_PORT:-18080}/api/v1
JSON='Content-Type: application/json'
```

Регистрация и вход (токен лежит в поле `token`):

```bash
curl -s -X POST $API/register -H "$JSON" \
  -d '{"email":"anna@example.com","password":"correct-horse-battery","name":"Анна"}'
curl -s -X POST $API/register -H "$JSON" \
  -d '{"email":"boris@example.com","password":"correct-horse-battery","name":"Борис"}'

ANNA=$(curl -s -X POST $API/login -H "$JSON" \
  -d '{"email":"anna@example.com","password":"correct-horse-battery"}' | sed -E 's/.*"token":"([^"]+)".*/\1/')
BORIS=$(curl -s -X POST $API/login -H "$JSON" \
  -d '{"email":"boris@example.com","password":"correct-horse-battery"}' | sed -E 's/.*"token":"([^"]+)".*/\1/')
```

Команда и приглашение. Создатель команды становится владельцем, приглашают по email, в ответе `user_id` приглашённого:

```bash
TEAM=$(curl -s -X POST $API/teams -H "$JSON" -H "Authorization: Bearer $ANNA" \
  -d '{"name":"Разработка"}' | sed -E 's/^\{"id":([0-9]+),.*/\1/')
BORIS_ID=$(curl -s -X POST $API/teams/$TEAM/invite -H "$JSON" -H "Authorization: Bearer $ANNA" \
  -d '{"email":"boris@example.com","role":"member"}' | sed -E 's/.*"user_id":([0-9]+).*/\1/')
curl -s $API/teams -H "Authorization: Bearer $BORIS"
```

Задача с исполнителем, список с фильтрами и страницы по курсору:

```bash
TASK=$(curl -s -X POST $API/tasks -H "$JSON" -H "Authorization: Bearer $ANNA" \
  -d "{\"team_id\":$TEAM,\"title\":\"Подготовить релиз\",\"description\":\"Собрать changelog\",\"assignee_id\":$BORIS_ID}" \
  | sed -E 's/^\{"id":([0-9]+),.*/\1/')
curl -s -X POST $API/tasks -H "$JSON" -H "Authorization: Bearer $ANNA" \
  -d "{\"team_id\":$TEAM,\"title\":\"Обновить зависимости\"}" >/dev/null

curl -s "$API/tasks?team_id=$TEAM&status=todo&assignee_id=$BORIS_ID&limit=20&offset=0" -H "Authorization: Bearer $ANNA"
curl -s "$API/tasks?team_id=$TEAM&limit=1" -H "Authorization: Bearer $ANNA"
```

В ответе списка поле `next_cursor` равно `id` последней задачи страницы. Передайте его в `cursor`, чтобы получить
следующую страницу; `null` означает, что дальше ничего нет:

```bash
NEXT=$(curl -s "$API/tasks?team_id=$TEAM&limit=1" -H "Authorization: Bearer $ANNA" | sed -E 's/.*"next_cursor":([0-9]+).*/\1/')
curl -s "$API/tasks?team_id=$TEAM&limit=1&cursor=$NEXT" -H "Authorization: Bearer $ANNA"
```

Обновление требует все поля и текущую `version`. Борис как исполнитель может менять только статус:

```bash
curl -s -X PUT $API/tasks/$TASK -H "$JSON" -H "Authorization: Bearer $BORIS" \
  -d "{\"title\":\"Подготовить релиз\",\"description\":\"Собрать changelog\",\"status\":\"done\",\"assignee_id\":$BORIS_ID,\"version\":1}"
```

Повтор с той же версией получает `409` и актуальную версию в `error.details.current_version`:

```bash
curl -s -X PUT $API/tasks/$TASK -H "$JSON" -H "Authorization: Bearer $BORIS" \
  -d "{\"title\":\"Подготовить релиз\",\"description\":\"Собрать changelog\",\"status\":\"in_progress\",\"assignee_id\":$BORIS_ID,\"version\":1}"
```

Борис не вправе менять название, это `403`:

```bash
curl -s -X PUT $API/tasks/$TASK -H "$JSON" -H "Authorization: Bearer $BORIS" \
  -d "{\"title\":\"Другое название\",\"description\":\"Собрать changelog\",\"status\":\"done\",\"assignee_id\":$BORIS_ID,\"version\":2}"
```

История, комментарии и отчёт (отчёт доступен только владельцу и администратору):

```bash
curl -s $API/tasks/$TASK/history -H "Authorization: Bearer $BORIS"
curl -s -X POST $API/tasks/$TASK/comments -H "$JSON" -H "Authorization: Bearer $BORIS" -d '{"content":"Готово, проверьте"}'
curl -s $API/tasks/$TASK/comments -H "Authorization: Bearer $ANNA"
curl -s $API/teams/$TEAM/stats -H "Authorization: Bearer $ANNA"
curl -s $API/teams/$TEAM/stats -H "Authorization: Bearer $BORIS"
```

Управление участниками (роль меняет только владелец; удалённый участник снимается с исполнителей, см. [Решения](#решения)):

```bash
curl -s -X PATCH $API/teams/$TEAM/members/$BORIS_ID -H "$JSON" -H "Authorization: Bearer $ANNA" -d '{"role":"admin"}'
curl -s -o /dev/null -w '%{http_code}\n' -X DELETE $API/teams/$TEAM/members/$BORIS_ID -H "Authorization: Bearer $ANNA"
```

Все ошибки приходят в одном формате, `request_id` совпадает с заголовком `X-Request-Id` и строками лога:

```json
{"error": {"code": "forbidden", "message": "your role cannot change: title", "request_id": "6ff2c9e0d1a45b87"}}
```

## Миграции

Миграции только вперёд, лежат в `internal/db/migrations/*.sql` и встроены в бинарник. Приложение применяет
непримённые файлы по порядку имён при каждом старте и записывает их в таблицу `schema_migrations`. Параллельный
запуск нескольких копий сериализуется через `GET_LOCK`, повторный старт ничего не делает.

Добавить миграцию: положить файл `0002_что_делает.sql` рядом с `0001_init.sql` и перезапустить приложение
(`docker compose up --build -d app`). Уже применённые файлы менять нельзя. Проверить, что применено:

```bash
docker compose exec mysql sh -c 'mysql -u root -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE" -e "SELECT * FROM schema_migrations"'
```

## Тесты

Go запускается в контейнере `tools`, на хост ничего ставить не нужно.

```bash
docker compose run --rm tools gofmt -l .
docker compose run --rm tools go vet ./...
docker compose run --rm tools go test -race -count=1 ./...
```

`gofmt -l .` должен ничего не печатать. Один тест: `docker compose run --rm tools go test -run TestCanInvite ./internal/team/`.

Контейнер `tools` работает от пользователя `1000:1000`, чтобы не создавать на хосте файлы от root. Если ваш uid другой,
перед командами выполните `export UID GID=$(id -g)`.

Интеграционные тесты идут на настоящем MySQL под тегом `integration`. Сервис `integration` сам поднимает MySQL и
для каждого теста создаёт временную базу с миграциями проекта (удаляется после теста):

```bash
docker compose run --rm integration go test -race -count=1 ./...
docker compose run --rm integration go test -race -count=1 -run TestReportAccess ./internal/stats/
```

Что проверяют тесты кроме обычных юнит-тестов:

- **Отчёт** (`internal/stats`): чужая команда, задачи старше 30 дней, граница окна, ничья в топе, больше трёх
  исполнителей, пустая команда, права.
- **Блокировки** (`internal/task`, `internal/team`): переназначение задачи против удаления участника на большой
  таблице и приглашение против удаления участника не должны давать дедлоков.
- **Курсор** (`internal/task`): обход списка без пропусков и повторов, фильтры, ключи кеша.
- **Спецификация** (`api`, `internal/server`): документ валиден, маршруты и коды ошибок совпадают с кодом в обе стороны;
  контрактный тест проходит весь сценарий и проверяет каждый запрос и ответ по схемам из `openapi.yaml`.
- **Конфигурация**: каждая переменная окружения из кода описана в этом README.

## Уборка

Остановить всё, ничего не удаляя: `docker compose stop`. Удалить контейнеры и базу проекта, образы оставить:
`docker compose down -v`. Удалить всё, что создал проект (контейнеры, тома, сеть и собранные образы):

```bash
docker compose --profile tools --profile demo down -v --rmi local --remove-orphans
```

Команда затрагивает только ресурсы проекта `tasksvc`: образы `mysql`, `redis` и `golang` не удаляются.
Файл `.env` остаётся, его можно удалить вручную.

## Решения

Пробелы ТЗ и как они закрыты:

| Что не определено в ТЗ | Решение |
|---|---|
| Как менять роли | `PATCH /api/v1/teams/{id}/members/{user_id}`, только владелец; роль владельца менять и назначать нельзя |
| Как удалять участников | `DELETE /api/v1/teams/{id}/members/{user_id}`; владельца и себя удалить нельзя; администратор удаляет только участников |
| Как приглашать | По email зарегистрированного пользователя. Владелец приглашает с ролью `admin` или `member`, администратор только `member`. Роль `owner` приглашением не выдаётся |
| Статусы задач | `todo`, `in_progress`, `done` |
| Когда ставится `closed_at` | При переходе в `done`; сбрасывается при выходе из `done` |
| Чужая команда или задача | `404`, как будто их нет. Участник команды без права получает `403`. Без права на приглашение ответ `403` приходит раньше поиска email |
| Задачи удаляемого участника | Он снимается с исполнителей **всех** задач команды, в том числе закрытых, и каждое снятие пишется в историю от имени удалившего (см. отчёт ниже) |
| Кто может комментировать | Любой участник команды задачи, не только исполнитель. Читать комментарии и историю тоже могут все участники |
| Смена `team_id` задачи | Не поддерживается: команда задачи не меняется |
| Форма `PUT /tasks/{id}` | Нужны все поля и `version`; `assignee_id: null` снимает исполнителя, пропуск поля даёт `400`. Права проверяются по реально изменившимся полям, поэтому прежние значения присылать безопасно |
| Пустое изменение | `200` без записи в историю и без роста `version` |
| Порядок списка и страницы | `id` по убыванию (новые первыми). `limit` (по умолчанию 20, максимум 100) и `offset` работают как в ТЗ; дополнительно есть `cursor`, он несовместим с `offset` |
| Повторная регистрация | `409 email_taken`: раскрывает, что email занят, но так проще пользователю. Вход таких сведений не раскрывает: ошибка и время ответа одинаковы для неизвестного email и неверного пароля |
| Права исполнителя на поля | Исполнитель меняет только `status`. Автор задачи меняет все поля. Владелец и администратор команды меняют любую задачу. Если человек автор и исполнитель одновременно, права складываются |

Определения отчёта `GET /api/v1/teams/{team_id}/stats` (доступен владельцу и администратору, участнику `403`):

- **Задачи по статусам**: статусы без задач возвращаются с нулём.
- **Топ-3 исполнителей** по числу задач, закрытых за последние 30 дней. Граница включительно, считается по
  *текущему* исполнителю задачи. При равенстве выше тот, у кого меньше `user_id`. Закрытые задачи без исполнителя в топ не попадают.
  Поскольку удаление участника снимает его и с закрытых задач, он пропадает из топа. Это сознательно: исполнитель
  всегда участник команды.
- **Среднее время закрытия**: от создания до `closed_at` по всем задачам команды с непустым `closed_at`, то есть по тем,
  что сейчас в статусе `done`, в секундах. Если закрытых нет, `0`.
- **Комментарии**: число комментариев ко всем задачам команды.
- Команда без задач даёт нули и пустой список, а не `null`.
- Один SQL-запрос из четырёх отдельных CTE (по одной на метрику): общий `JOIN` задач с комментариями размножил бы строки
  и исказил и счётчики, и среднее. В каждой CTE стоит фильтр по `team_id`.

Курсорная пагинация: `next_cursor` равен `id` последней задачи страницы (или `null`, если дальше ничего нет),
передаётся в `cursor`. `total` без курсора считает все задачи под фильтрами, **с курсором** только те, что лежат после него.

## Как устроено

Код разложен по слоям `handler → service → repository`. Правила доступа живут только в service, SQL лежит
в repository (и в миграциях). Сервисы не знают про HTTP: они возвращают ошибки по видам (`internal/apperr`), а в статусы их превращает
слой `httpx`. Логгер запроса идёт через контекст (`internal/logx`), поэтому повторы транзакций и ошибки кеша
в логе тоже содержат `request_id`.

```
cmd/server        запуск, корректная остановка по SIGINT/SIGTERM
api               openapi.yaml и страница Swagger UI (встроены в бинарник)
internal/user     регистрация и вход          internal/team   команды, участники, роли
internal/task     задачи, история, комментарии internal/stats  отчёт по команде
internal/auth     JWT                         internal/ratelimit  ограничение частоты
internal/cache    кеш списка задач, Redis-клиент internal/breaker  предохранитель
internal/db       подключение, транзакции, миграции    internal/httpx   ответы, ошибки, middleware
```

**Права таблицами.** Права на поля задачи описаны данными в `internal/task/permissions.go`: строка «роль в команде
и отношение к задаче (автор, исполнитель) → какие поля можно менять», права подошедших строк складываются.
Права на участников устроены так же (`internal/team/permissions.go`). Сервис спрашивает таблицу, юнит-тесты идут
прямо по ней, новое правило добавляется строкой.

**Параллельные обновления.** `PUT` требует `version`. В транзакции задача читается через `SELECT ... FOR UPDATE`,
версия сравнивается с присланной (при несовпадении `409` и текущая версия в ответе), права проверяются по этой же
строке, история строится от неё, `version` растёт на 1. Два параллельных `PUT` с одной версией дают один `200` и один `409`,
в истории одна запись. Создание и обновление задачи пишут историю в той же транзакции.

**Порядок блокировок.** Везде один порядок: строка команды (`teams`), затем строки участников (`team_members`),
затем строка задачи (`tasks`). Без него обновление и удаление участника уходили в дедлок: удаление снимает исполнителя
по индексу `(team_id, assignee_id, id)`, а обновление идёт по первичному ключу, то есть строки берутся в обратном
порядке, и строка участника их не разводит, потому что прежний исполнитель при обновлении не блокируется. Поэтому
создание и обновление задачи, а также приглашение берут команду `FOR SHARE`, а удаление участника `FOR UPDATE`.
Смене роли команда не нужна. Вдобавок `db.InTx` повторяет транзакцию при дедлоке (MySQL 1213) до трёх попыток и пишет
каждый повтор в лог. Оба сценария покрыты интеграционными тестами, проверено мутациями: без блокировки тесты падают.

**Кеш списка задач.** Список команды кешируется в Redis на 5 минут. Ключ `tasks:list:{команда}:{поколение}:{фильтры}`
включает нормализованные фильтры, страницу и курсор. У каждой команды есть счётчик поколения `tasks:gen:{команда}`;
любое изменение задач увеличивает его, и все старые ключи команды становятся недостижимыми.

- Поколение читается **до** запроса в базу: запрос, начавшийся раньше изменения, запишет данные под старый ключ,
  который уже никто не прочитает.
- Инвалидация идёт **после** коммита, из одной точки (`TaskLists.InvalidateTeam`), через которую проходят `Create`
  и `Update` задач и удаление участника (оно снимает исполнителей). Она не зависит от отмены запроса клиентом.
- У счётчиков нет TTL, а Redis запущен с `volatile-lru`: вытеснять можно только ключи с TTL. С `allkeys-lru` вытесненный
  счётчик вернулся бы к нулю и открыл устаревшие записи.
- Проверка членства в команде выполняется до обращения к кешу, поэтому чужая команда получает `404` и при тёплом кеше.

**Redis недоступен.** Любая ошибка Redis считается промахом: список идёт из базы, а ограничитель частоты пропускает запрос.
Вокруг всех вызовов Redis стоит предохранитель (`internal/breaker`) поверх таймаута 200 мс. Пять сбоев подряд размыкают цепь,
пока она разомкнута, вызовы отклоняются мгновенно; через 5 секунд пропускается одна проба (half-open), успех замыкает цепь.
Сбоем считаются сетевые ошибки и таймауты, но не «ключа нет», не ошибка команды и не отмена запроса клиентом.
Если инвалидацию выполнить не удалось (Redis недоступен или цепь разомкнута), команда помечается как pending: пока
пометка стоит, чтения этой команды идут в базу, а перед первым чтением после восстановления инвалидация повторяется.
Иначе Redis, вернувшийся со старыми данными, отдал бы устаревший список.

**Ограничение частоты.** Счётчик на окно в 1 минуту в Redis (`INCR` и `EXPIRE` одним Lua-скриптом, чтобы ключ никогда
не остался без TTL). `register` и `login` считаются отдельно по IP клиента, остальные маршруты по пользователю. При
превышении: `429`, заголовок `Retry-After` и `error.details.retry_after_seconds`. IP берётся из адреса соединения.
`X-Forwarded-For` учитывается только от прокси из `TRUSTED_PROXIES`: заголовок читается справа налево, доверенные прокси
пропускаются, первый недоверенный адрес и есть клиент. IPv6-клиенты группируются по подсети `/64`.

**Логи.** Структурированные JSON-логи (`log/slog`) с `request_id` в каждой строке. Пароли, токены и хеши в логи и в ответы не попадают.

**База.** Кодировка соединения `utf8mb4_0900_ai_ci` совпадает с умолчанием схемы MySQL 8, иначе выражения над колонками
разных таблиц в `UNION` падают с `Illegal mix of collations`.

## Ограничения

- **Окно ограничителя фиксированное**, поэтому на стыке двух окон клиент может сделать до двойного лимита подряд.
  Для защиты от перебора пароля этого достаточно.
- **За Docker все клиенты на одном IP.** Запросы к опубликованному порту приходят из сети compose с адреса шлюза
  (например `172.20.0.1`), поэтому все локальные клиенты делят одну корзину `register` и `login`. Лимит по умолчанию 10 в минуту:
  скрипты, регистрирующие много пользователей, должны либо укладываться в него, либо запускать сервис с большим
  `RATE_LIMIT_AUTH_PER_MINUTE`. За настоящим прокси укажите его адрес в `TRUSTED_PROXIES`.
- **Отметка pending живёт в памяти процесса.** При нескольких репликах приложения или после перезапуска процесса она
  теряется, и устаревшие записи кеша ограничены только TTL в 5 минут.
- **Предохранитель свой у каждого процесса**, состояние между репликами не общее.
- **Токены без отзыва.** JWT живёт `JWT_TTL`, отозвать его до истечения нельзя; обновления токенов (refresh) нет.
- **Нет** удаления пользователей и команд, смены пароля, смены `team_id` у задачи.
- **Swagger UI** грузится с CDN и без интернета не откроется (сам API работает).
- **Один экземпляр MySQL и Redis** без репликации и бэкапов, Redis без персистентности: это кеш и счётчики лимитов.
